## 1. 项目是什么

一个**跨境电商数据中台**，核心是「用一条自动化流水线，把公开数据和订单数据变成经营决策」：

| 能力 | 说明 |
|---|---|
| RPA 采集 | Playwright 定时抓亚马逊 Best Sellers 榜单（排名/价格/评分/评论数） |
| 订单导入 | 卖家后台导出的订单 CSV，清洗后自动入库 |
| 数据仓库 | 三张表（商品维度 + 榜单事实 + 订单事实）的维度建模 |
| 指标体系 | 12 项经营指标 + 6 项市场竞品指标，共 18 项 |
| 经营大屏 | Streamlit 可视化，KPI 卡片 + 趋势图 |
| 日报推送 | 自动生成经营日报，推送到飞书群 |
| AI 解读 | 手写 Agent 循环调 DeepSeek，自动归因异动、输出选品报告 |

一句话概括：**它不是一个"采集脚本"，而是一条「采集 → 建模 → 分析 → 决策」的完整数据流水线，无人值守自动运行。**

## 2. 技术栈总览（为什么选这些）

| 层 | 选型 | 为什么选它 |
|---|---|---|
| 语言 | Python 3.11 | 生态全，pandas/SQLAlchemy 都是一等公民 |
| 数据库 | PostgreSQL 18 | 支持事务、`ON CONFLICT` 原生 upsert、`RETURNING`；生产级 |
| ORM | SQLAlchemy 2.x | 声明式模型 + 连接池 + 方言无关；换库只改一行连接串 |
| 驱动 | `psycopg2-binary` | SQLAlchemy 的 PostgreSQL 默认驱动，预编译免装编译工具链 |
| 数据处理 | pandas | `read_sql` 直读成 DataFrame，指标计算全在内存里做 |
| 浏览器自动化 | Playwright | 真实浏览器指纹，比 requests 更抗反爬；自动等 DOM |
| 定时调度 | APScheduler | 纯 Python，Cron 表达式，常驻进程内 |
| 可视化 | Streamlit + Altair | 不用写前端，Python 直接出图 |
| 大模型 | DeepSeek（`openai` SDK 兼容） | 国内直连、便宜、中文好；改模型只改配置 |
| 测试 | pytest | 18 项测试覆盖解析/清洗/指标口径/Agent 工具 |

**核心设计哲学**：数据库这件事**只在一个文件里碰**（`database/db.py`），其余所有代码都以「拿到 DataFrame 或 ORM 对象」为前提，不关心底层是什么库。这是能在一个下午把 MySQL 换成 PostgreSQL 的原因。

**关键思想：分层单向依赖。** 上层可以调下层，下层绝不反向依赖上层。
- `analytics/` 和 `agent/` 都不直接连数据库，只调 `database.metrics` 的函数
- `metrics.py` 是唯一的「读」出口，`collectors/` 是唯一的「写」入口
- 换数据库、换指标口径、换可视化，各自独立改动，互不波及

## 4. 数据库层详解（本文重点）

### 4.1 为什么用「维度建模」（星型模型）

维度建模是数据仓库的标准打法，核心是把数据分成两类：

| 类型 | 前缀 | 特征 | 本项目中的表 |
|---|---|---|---|
| 维度表 | `dim_` | 描述「谁/什么」，相对静态，一行一个实体 | `dim_product` |
| 事实表 | `fact_` | 描述「发生了什么」，随事件增长，一行一个事件 | `fact_snapshot` / `fact_order` |

**为什么不全塞一张表？**
- 商品标题/品类是**描述性属性**，每次都存一遍是冗余 → 抽到 `dim_product`
- 榜单快照和订单是两种完全不同粒度的**度量事件**，混在一起指标口径会互相污染 → 拆成两张 `fact`
- 事实表只存 `asin` 外键，需要标题时 `JOIN` 维度表拿

### 4.2 为什么用 ORM 而不是手写 SQL

| 做法 | 问题 |
|---|---|
| 手写 `CREATE TABLE` + 字符串拼 SQL | 换库要改一遍；字段名打错运行时才炸；无类型提示 |
| **SQLAlchemy 声明式模型** | 一处定义，建表/查询/类型全自动；换库只改连接串 |

本项目 90% 的数据库操作走 ORM，只有 `metrics.py` 里为了配合 pandas 用了原生 SQL（**读多写少、且需要 JOIN 出宽表**，用 SQL 更直观）。

### 4.3 建模时用的三个关键约束类型

理解这三个，就理解了幂等设计：

| 约束 | 作用 | 本项目用在哪 |
|---|---|---|
| **主键 PRIMARY KEY** | 唯一标识一行，天然去重 | `dim_product.asin`；两张 fact 表的自增 `id` |
| **唯一约束 UNIQUE** | 组合字段不可重复，upsert 的「撞点」 | `fact_snapshot(asin, captured_at, position)`；`fact_order(order_id, asin)` |
| **索引 INDEX** | 加速查询，不强制唯一 | `category`、`order_date`、`(asin, captured_at)` |

## 5. 三张表的设计（逐字段拆解）

### 5.1 `dim_product` — 商品维度表（一个 ASIN 一行）

```python
class DimProduct(Base):
    __tablename__ = "dim_product"

    asin:       Mapped[str]       = mapped_column(String(10), primary_key=True)
    title:      Mapped[str]       = mapped_column(String(500), nullable=False)
    brand:      Mapped[str | None]= mapped_column(String(100))
    category:   Mapped[str]       = mapped_column(String(100), index=True)
    url:        Mapped[str | None]= mapped_column(String(500))
    first_seen: Mapped[datetime]  = mapped_column(DateTime, default=datetime.now)
    updated_at: Mapped[datetime]  = mapped_column(DateTime, default=datetime.now,
                                                  onupdate=datetime.now)
```

| 字段 | 类型 | 设计意图 |
|---|---|---|
| `asin` | `VARCHAR(10)` **主键** | 用**业务主键**（自然键），不是自增 id。因为 ASIN 本身就是全球唯一标识，直接拿来当主键最省事，也让「同一个商品」的 upsert 极其简单 |
| `title` | `VARCHAR(500)` NOT NULL | 亚马逊标题很长，500 够用；非空，因为它是识别商品的核心 |
| `brand` | `VARCHAR(100)` 可空 | **预留字段**，后续从商品详情页补充；现在允许为空 |
| `category` | `VARCHAR(100)` 索引 | 采集来源类目。**建索引**是因为市场分析几乎都按类目聚合（`GROUP BY category`） |
| `url` | `VARCHAR(500)` 可空 | 商品链接，便于人工复核 |
| `first_seen` | `DATETIME` | 首次发现时间，写入时由 Python 的 `datetime.now` 填 |
| `updated_at` | `DATETIME` | 最后更新时间，**`onupdate=datetime.now`** 让 SQLAlchemy 每次 UPDATE 时自动刷新 |

> **设计要点**：`first_seen` 与 `updated_at` 分离，可以回答「这个商品是长期在榜，还是刚冒出来的」——但注意 `updated_at` 只在标题变更时才刷新（见第 6.5 节的 upsert 逻辑）。

### 5.2 `fact_snapshot` — 榜单快照事实表（每次采集追加一行）

```python
class FactSnapshot(Base):
    __tablename__ = "fact_snapshot"
    __table_args__ = (
        UniqueConstraint("asin", "captured_at", "position", name="uq_snapshot"),
        Index("ix_snapshot_asin_time", "asin", "captured_at"),
    )

    id:           Mapped[int]        = mapped_column(Integer, primary_key=True, autoincrement=True)
    asin:         Mapped[str]        = mapped_column(String(10))
    captured_at:  Mapped[datetime]   = mapped_column(DateTime, default=datetime.now)
    position:     Mapped[int]        = mapped_column(Integer)
    price:        Mapped[float|None] = mapped_column(Float)
    rating:       Mapped[float|None] = mapped_column(Float)
    review_count: Mapped[int|None]   = mapped_column(Integer)
```

| 字段 | 类型 | 设计意图 |
|---|---|---|
| `id` | 自增主键 | 快照是**事件**，没有天然的单列主键（同一个 ASIN 会有很多行），所以用代理键自增 id |
| `asin` | `VARCHAR(10)` | 外键指向 `dim_product.asin`（**逻辑外键**，见下方说明） |
| `captured_at` | `DATETIME` | 采集时间，同一批采集的所有行共用同一个时间戳 |
| `position` | `INT` | 榜单排名（第几名） |
| `price` | `FLOAT` 可空 | 价格 USD，**可空**因为部分商品页不显示价格 |
| `rating` | `FLOAT` 可空 | 评分 0–5 |
| `review_count` | `INT` 可空 | 评论总数，**亚马逊不公开销量时的行业标准代理指标** |

**两条约束的分工**：

```python
UniqueConstraint("asin", "captured_at", "position")  # 同一时刻同一商品同一排名只有一行
Index("ix_snapshot_asin_time", "asin", "captured_at") # 加速「某商品随时间的排名变化」
```

- 唯一约束是**数据质量防线**：防止同一次采集因重试而重复插入
- 组合索引是**查询加速器**：`rank_changes()` 要按 ASIN 拉时间序列，索引正好命中

> **关于外键**：这里用 `asin` 关联但**没有建数据库级 FOREIGN KEY**。因为采集时可能先写入快照、商品维度表稍后补（或商品已下架），强外键会让采集失败。这是数据仓库「先落地、后治理」的常见取舍——`metrics.load_snapshots()` 用 `LEFT JOIN` 兼容孤儿数据。

### 5.3 `fact_order` — 订单事实表（一行一个订单行项目）

```python
class FactOrder(Base):
    __tablename__ = "fact_order"
    __table_args__ = (
        UniqueConstraint("order_id", "asin", name="uq_order_asin"),
        Index("ix_order_date", "order_date"),
    )

    id:          Mapped[int]   = mapped_column(Integer, primary_key=True, autoincrement=True)
    order_id:    Mapped[str]   = mapped_column(String(50))
    order_date:  Mapped[datetime] = mapped_column(DateTime)
    asin:        Mapped[str]   = mapped_column(String(10))
    title:       Mapped[str|None] = mapped_column(String(500))
    category:    Mapped[str|None] = mapped_column(String(50))
    quantity:    Mapped[int]   = mapped_column(Integer, default=1)
    unit_price:  Mapped[float] = mapped_column(Float)
    currency:    Mapped[str]   = mapped_column(String(10), default="USD")
    channel:     Mapped[str]   = mapped_column(String(30), default="amazon")
    status:      Mapped[str]   = mapped_column(String(30), default="Shipped")
    imported_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.now)
```

| 字段 | 类型 | 设计意图 |
|---|---|---|
| `id` | 自增主键 | 代理键，理由同上 |
| `order_id` | `VARCHAR(50)` | 亚马逊订单号，形如 `114-1234567-0000001` |
| `order_date` | `DATETIME` **索引** | 几乎所有经营指标都按时间聚合（月度趋势/日均 GMV），必须建索引 |
| `asin` | `VARCHAR(10)` | 商品 |
| `title` / `category` | 可空 | **快照冗余**：订单里的商品信息单独存一份，即使维度表后来变了，历史订单口径不变 |
| `quantity` | `INT` default 1 | 购买数量 |
| `unit_price` | `FLOAT` | 成交单价（**不是标价**，含折扣） |
| `currency` / `channel` | 默认 USD / amazon | 多渠道扩展预留 |
| `status` | 默认 `Shipped` | 取值 `Shipped` / `Pending` / `Cancelled`，**决定收入口径** |
| `imported_at` | `DATETIME` | 导入时间，用于追溯 |

**为什么唯一约束是 `(order_id, asin)` 而不是 `order_id`？**

因为亚马逊订单报表是**一个订单行一个 ASIN 一行**——一个订单买了 3 种商品就有 3 行，`order_id` 会重复出现。所以单靠 `order_id` 不能唯一，必须加上 `asin` 组成复合唯一键。

**为什么 `title`/`category` 要冗余存一遍？**

这是事实表的常见做法（**退化维度**）：订单是历史事实，商品维度表的数据可能被后续采集覆盖。把下单时的标题快照存进订单，保证「去年的订单看的是去年的商品名」，指标口径可复现。

### 5.5 三张表在不同操作下的行为对照

这是最容易记混的地方，一张表说清：

| 表 | 重复采集/导入时 | 机制 | 行数变化 |
|---|---|---|---|
| `fact_snapshot` | **累计追加** | 直接 `session.add()`，`captured_at` 每次都不同 | 每次采集 +240 行，持续增长 |
| `dim_product` | **更新不新增** | `session.get()` 按主键查，命中只改 `title` | 基本不变，遇到新 ASIN 才 +1 |
| `fact_order` | **更新不新增** | `ON CONFLICT DO UPDATE` 撞 `uq_order_asin` | 不变，只更新 `quantity` |

## 6. 数据库是怎么被驱动的（引擎 / 会话 / 建表 / 读写 / 幂等）

这是全文最核心的一节——**从连接串到一行数据落库，中间到底发生了什么**。

### 6.1 全项目唯一的数据库入口：`database/db.py`

整个项目**只有这一个文件**负责「怎么连数据库」，它只有 60 行，但决定了后面所有代码怎么写：

```python
def _build_engine():
    global _Session
    cfg = load_config()["database"]                     # 1. 读 YAML 配置
    base = (
        f"postgresql+psycopg2://{cfg['user']}:{quote_plus(cfg['password'])}"
        f"@{cfg['host']}:{cfg['port']}"                 # 2. 拼连接串（密码 URL 编码）
    )
    # 3. 先连到默认库 postgres，检查目标库是否存在
    server = create_engine(f"{base}/postgres", isolation_level="AUTOCOMMIT",
                           pool_pre_ping=True)
    with server.connect() as conn:
        exists = conn.execute(
            text("SELECT 1 FROM pg_database WHERE datname = :db"), {"db": cfg["db"]}
        ).scalar()
        if not exists:
            conn.execute(text(f'CREATE DATABASE "{cfg["db"]}"'))   # 4. 不存在才建库
    server.dispose()

    # 5. 连到目标库，造会话工厂
    engine = create_engine(f"{base}/{cfg['db']}", pool_pre_ping=True)
    _Session = sessionmaker(bind=engine, expire_on_commit=False)
    return engine
```

**逐点拆解这些设计决策：**

| 代码 | 为什么这么写 |
|---|---|
| `postgresql+psycopg2://` | SQLAlchemy 的**方言前缀**。`postgresql` 告诉它用 PG 方言，`psycopg2` 告诉它加载哪个驱动。换库就是换这个前缀（曾经是 `mysql+pymysql`） |
| `quote_plus(password)` | 密码里可能有 `@` `:` `/` 等字符，会破坏 URL 结构，必须转义。**所以你可以直接填明文密码，不用自己转** |
| `isolation_level="AUTOCOMMIT"` | PostgreSQL 的 `CREATE DATABASE` **不能在事务块里执行**。默认 SQLAlchemy 会在事务中跑 SQL，所以建库这条必须开自动提交 |
| 先连 `/postgres` 库 | 目标库还不存在时没法连它，只能先连 PG 自带的 `postgres` 库，从「外部」建库 |
| `SELECT 1 FROM pg_database WHERE datname=:db` | PostgreSQL 没有 `CREATE DATABASE IF NOT EXISTS`（MySQL 有）。所以手动查 `pg_database` 系统表，**不存在才建**，实现幂等 |
| `pool_pre_ping=True` | 连接池取连接前先 ping 一下，网络闪断/数据库重启后自动重连。**常驻服务（调度器/大屏）必备** |
| `expire_on_commit=False` | commit 后对象不过期，可以继续读它。避免 commit 后再访问属性触发额外查询 |
| 全局 `_engine` / `_Session` + `get_engine()` 懒加载 | 引擎只建一次（连接池全局共享）。**模块导入时不连库**，第一次真正查询才连——这样 `pytest` 导包、`--help` 都不会误触发数据库连接 |

### 6.2 模型层：`database/models.py`

三张表的定义（第 5 节已详述），关键在基类：

```python
class Base(DeclarativeBase):
    pass
```

SQLAlchemy 2.x 的新式声明基类。所有模型继承它，SQLAlchemy 就自动收集到 `Base.metadata` 里——建表时一个 `create_all` 搞定。

类型映射（声明 → PostgreSQL 实际类型）：

| 声明 | PostgreSQL 实际类型 |
|---|---|
| `String(10)` | `VARCHAR(10)` |
| `Integer` + `autoincrement=True` | `SERIAL`（实际是 identity 序列） |
| `Float` | `DOUBLE PRECISION` |
| `DateTime` | `TIMESTAMP WITHOUT TIME ZONE` |
| `primary_key=True` | `PRIMARY KEY` |

### 6.3 建表：`database/init_db.py`

```python
engine = get_engine()
Base.metadata.create_all(engine)
```

`create_all` 是**幂等**的——它先查库里已有哪些表，只创建缺失的，已存在的不动。所以随便跑多少次都安全。**注意**：它只建表，**不改表**——字段改了要删表重建或上迁移工具（如 Alembic）。

### 6.4 写路径一：ORM 会话（采集器落库）

`collectors/amazon_bestseller.py` 的 `save_to_db()`，演示了**维度表的 upsert**：

```python
def save_to_db(cards, category):
    session = get_session()          # 从会话工厂拿一个会话
    now = datetime.now()             # 一批采集共用一个时间戳
    try:
        for c in cards:
            product = session.get(DimProduct, c["asin"])   # ① 按主键查
            if product is None:                            # ② 不存在 → 新增
                product = DimProduct(asin=c["asin"], title=c["title"] or "未知",
                                     category=category, url=c["url"])
                session.add(product)
            elif c["title"]:                               # ③ 已存在 → 只更新标题
                product.title = c["title"]

            session.add(FactSnapshot(                      # ④ 快照无条件追加
                asin=c["asin"], captured_at=now, position=c["rank"],
                price=c["price"], rating=c["rating"], review_count=c["reviews"],
            ))
        session.commit()                                   # ⑤ 一次性提交（隐式事务）
    finally:
        session.close()                                    # ⑥ 必须关，归还连接
```

**这段代码体现了三个关键概念：**

1. **Unit of Work（工作单元）**：`session.add()` 只是把对象放进「待提交」队列，`commit()` 才真正发 SQL。期间 SQLAlchemy 知道哪些是 INSERT、哪些是 UPDATE（靠对象状态跟踪）。
2. **身份映射（Identity Map）**：`session.get(DimProduct, asin)` 会先看会话里有没有这个对象，有就直接返回，避免同一对象在内存里出现两份。
3. **隐式事务**：`commit()` 前所有改动在一个事务里。要么全成功，要么全回滚——**一批 60 个商品不会出现「写了一半」的脏状态**。

> **为什么 `finally: session.close()` 是必须的？** 会话不关，连接不会归还连接池，池子会被耗尽。写法固定为 `try / commit / finally close`。

### 6.5 PostgreSQL 原生 upsert（订单导入）

`collectors/order_importer.py` 用的是**数据库级**的 upsert，比「先查再写」更高效、更抗并发：

```python
from sqlalchemy.dialects.postgresql import insert     # ← PostgreSQL 专属方言

stmt = insert(FactOrder).values(rows)                  # 批量构造 INSERT
stmt = stmt.on_conflict_do_update(
    constraint="uq_order_asin",                        # 撞 (order_id, asin) 唯一约束时
    set_={"quantity": stmt.excluded.quantity},         # 把 quantity 更新为新值
)
with get_engine().begin() as conn:                     # begin() = 自动事务 + 自动提交/回滚
    conn.execute(stmt)
```

生成的 SQL 大致是：

```sql
INSERT INTO fact_order (order_id, order_date, asin, ..., quantity)
VALUES (...), (...), ...
ON CONFLICT ON CONSTRAINT uq_order_asin
DO UPDATE SET quantity = EXCLUDED.quantity;
```

**关键概念：**
- `EXCLUDED` 是 PostgreSQL 的伪表，代表「本次本来要插入的那行」。`EXCLUDED.quantity` 就是新数据的数量。
- `insert(FactOrder)` 是**方言专属**的（从 `sqlalchemy.dialects.postgresql` 导入），MySQL 要用 `dialects.mysql` 且方法名不同（`on_duplicate_key_update`）。**这是迁移时唯一需要改的数据库方言代码。**
- `engine.begin()` 上下文管理器：进块开事务，正常退出自动 `commit`，抛异常自动 `rollback`。**比手动 try/commit/except/rollback 干净得多。**

> **为什么订单导入用「批量 upsert」而不是 ORM 逐条？** 订单动辄几千行（本项目样本 8358 行），ORM 逐条 = 8358 次往返，慢；批量 INSERT 一条 SQL 搞定。**写多写少，选型不同**：采集 60 条用 ORM 清晰，订单 8000 条用 Core 高效。

### 6.6 读路径：pandas 直读成 DataFrame（`database/metrics.py`）

分析层不碰 ORM，直接用 SQL 读宽表：

```python
def load_snapshots() -> pd.DataFrame:
    df = pd.read_sql(
        """SELECT s.asin, s.captured_at, s.position, s.price, s.rating, s.review_count,
                  p.title, p.category
           FROM fact_snapshot s LEFT JOIN dim_product p ON p.asin = s.asin""",
        _engine(),
    )
    df["captured_at"] = pd.to_datetime(df["captured_at"])
    return df
```

**为什么读用原生 SQL 而不是 ORM？**
- 指标计算需要**宽表**（快照 + 维度 JOIN 后一起进 pandas），SQL 的 `JOIN` 表达最直接
- pandas 的 `read_sql` 直接把结果集变成 DataFrame，之后 `groupby`/`pivot`/`pct_change` 全在内存算
- 读操作不涉及对象状态跟踪，ORM 的价值体现不出来

**`LEFT JOIN` 的必要性**：保证即使 `dim_product` 里没有对应商品（孤儿快照），快照也不会丢——只是 `title`/`category` 为 `NaN`。

**懒加载引擎**：

```python
_ENGINE = None
def _engine():
    global _ENGINE
    if _ENGINE is None:
        _ENGINE = get_engine()
    return _ENGINE
```

作用同 6.1：**导入 metrics 模块时不连库**，第一次查询才连。对 Streamlit 这类常驻服务更稳健。

### 6.7 连接池：为什么不用手动管理连接

```
应用代码
  │ session / engine.connect()
  ▼
┌─────────────────────────────┐
│  SQLAlchemy 连接池（默认 5 个）│  ← 连接复用，避免每次 TCP 握手
│  pool_pre_ping=True          │  ← 取连接前验活，断了自动重连
└─────────────────────────────┘
  │ psycopg2
  ▼
PostgreSQL 18
```

**不要自己 `psycopg2.connect()` 然后到处传**——连接池帮你做了复用、健康检查、并发上限、归还管理。你只需要 `session.close()`。

## 附一：三张表的真实 DDL（`psql \d` 实测）

models.py 里的声明式模型，经 SQLAlchemy 翻译后，在 PostgreSQL 里实际长这样——**这是校验「声明 → 实际类型」映射的最硬证据**：

```sql
-- dim_product（商品维度）
CREATE TABLE dim_product (
    asin        varchar(10)  NOT NULL,
    title       varchar(500) NOT NULL,
    brand       varchar(100),
    category    varchar(100) NOT NULL,
    url         varchar(500),
    first_seen  timestamp    NOT NULL,
    updated_at  timestamp    NOT NULL,
    PRIMARY KEY (asin)
);
CREATE INDEX ix_dim_product_category ON dim_product (category);

-- fact_snapshot（榜单快照）
CREATE TABLE fact_snapshot (
    id           serial       NOT NULL,      -- Integer + autoincrement
    asin         varchar(10)  NOT NULL,
    captured_at  timestamp    NOT NULL,
    position     integer      NOT NULL,
    price        double precision,
    rating       double precision,
    review_count integer,
    PRIMARY KEY (id),
    CONSTRAINT uq_snapshot UNIQUE (asin, captured_at, position)
);
CREATE INDEX ix_snapshot_asin_time ON fact_snapshot (asin, captured_at);

-- fact_order（订单事实）
CREATE TABLE fact_order (
    id          serial       NOT NULL,
    order_id    varchar(50)  NOT NULL,
    order_date  timestamp    NOT NULL,
    asin        varchar(10)  NOT NULL,
    title       varchar(500),
    category    varchar(50),
    quantity    integer      NOT NULL,
    unit_price  double precision NOT NULL,
    currency    varchar(10)  NOT NULL,
    channel     varchar(30)  NOT NULL,
    status      varchar(30)  NOT NULL,
    imported_at timestamp    NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uq_order_asin UNIQUE (order_id, asin)
);
CREATE INDEX ix_order_date ON fact_order (order_date);
```

**读法提示**：
- `serial` 报的是 `integer NOT NULL DEFAULT nextval('fact_order_id_seq')`——PostgreSQL 的自增是靠**序列（sequence）**实现的，这是 `autoincrement=True` 的真实落地形态
- `timestamp` = `timestamp without time zone`，SQLAlchemy 的 `DateTime` 不带时区
- `double precision` 是 `Float` 的落地类型（8 字节浮点）
- 唯一约束在 DDL 里是 `CONSTRAINT uq_xxx UNIQUE (...)`——**upsert 的 `constraint="uq_order_asin"` 就是按这个名字找撞点**
